## 1. 무엇을 푸는 문제인가

대시보드는 같은 질문을 계속 반복합니다. "이 노드의 최근 1시간 CPU 를 1분 간격으로" 같은 조회가
화면을 열 때마다, 그리고 보는 사람 수만큼 InfluxDB 로 나갑니다.

그런데 이 조회에는 캐싱을 어렵게 만드는 성질이 하나 있습니다. **조회 구간이 상대 시간**입니다.
`range=1h` 는 "지금부터 1시간 전까지" 이므로 1초만 지나도 형식적으로는 다른 질문입니다.
그렇다고 매번 새로 조회하면 캐시가 의미가 없습니다.

풀어야 할 질문은 결국 **"얼마나 묵은 답까지 같은 답으로 봐도 되는가"** 이고,
그 답은 조회 자신이 들고 있습니다. `group_time=1m` 으로 1분 단위 집계를 요청했다면
**새 데이터 점은 1분에 한 번만 생깁니다.** 1분 안에는 몇 번을 물어도 실질적으로 같은 답입니다.

이 성질이 이 캐시의 설계 전체를 결정합니다.

> **용어**
> - **TTL / 유효기간**: 저장한 값이 살아 있는 시간
> - **fresh window(신선 구간)**: 그 값을 "아직 최신" 으로 취급하는 시간. 여기서는 조회의 `group_time`
> - **hit / miss**: 물어봤을 때 캐시에 있으면 hit, 없어서 저장소까지 가야 하면 miss
> - **예열(warming)**: 사용자가 보기 전에 미리 캐시를 채워두는 백그라운드 작업

## 2. 전체 그림

알아둘 전제 세 가지입니다.

- 캐시는 [Caffeine](https://github.com/ben-manes/caffeine) 으로 **직접** 만들었습니다.
  스프링의 `@Cacheable` 은 쓰지 않습니다 (이유는 아래 각 절에 나옵니다).
- 캐시는 전부 **매니저 프로세스 한 개의 메모리 안**에만 있습니다. 프로세스가 꺼지면 사라집니다.
- 캐시가 여러 겹입니다. 큰 것 둘(메트릭·CSP)과 그 밑을 받치는 작은 것들이 있습니다.

```
   화면(front) · insight(예측/이상탐지) · GPU 조회
            │  measurement, range, group_time, fields
            ▼
 ┌───────────────────────────────────────────────────────────┐
 │ ① 메트릭 결과 캐시  MonitoringCacheService                 │
 │                                                           │
 │    신선함   ─────────────────────────► 즉시 응답           │
 │    묵었음   ─► 즉시 응답 + 뒤에서 갱신 ─┐                   │
 │    없음     ─► 한 번만 로드 ───────────┤                   │
 └────────────────────────────────────────┼──────────────────┘
                                          ▼
 ┌───────────────────────────────────────────────────────────┐
 │ ② 보조 캐시  InfluxMetaCache / InfluxClientProvider        │
 │    보관정책 · 자원 존재 확인 · 측정항목 목록 · 공유 접속     │
 └────────────────────────────────────────┬──────────────────┘
                                          ▼
                                      InfluxDB
                                  (원본 / 다운샘플)

 ┌─ ③ 예열  MonitoringCacheWarmScheduler ───────────────────┐
 │   realtime(매분) · longrange(매시 5분) · overview(매분)   │
 └──────────────────────────────────────────────────────────┘

 ┌─ ④ CSP 모니터링 캐시  CspCacheService (+ 전용 예열) ──────┐
 │   cb-spider → 클라우드 API 응답                           │
 └──────────────────────────────────────────────────────────┘
```

| 계층 | 무엇을 담나 | 코드 |
|---|---|---|
| ① 메트릭 결과 캐시 | InfluxDB 조회 결과(그래프 데이터) | `service/cache/MonitoringCacheService.java` |
| ② 보조 캐시 | 보관정책, 존재 확인, 측정항목 목록, HTTP 접속 | `service/influx/InfluxMetaCache.java`, `InfluxClientProvider.java` |
| ③ 예열 | 위 ①을 미리 채우는 스케줄러 | `service/cache/MonitoringCacheWarmScheduler.java` |
| ④ CSP 캐시 | cb-spider 클라우드 사용량 응답 | `service/cache/CspCacheService.java` |

## 3. 메트릭 캐시 - 요청 하나가 지나가는 길

가장 중요한 그림입니다. 요청은 **세 갈래** 중 하나로 갑니다.

```
                          요청 도착
                             │
                             ▼
                   ┌──────────────────┐
                   │ 캐시에 있나?      │
                   └────┬────────┬────┘
                     있음         없음
                        │           │
                        ▼           │
              ┌──────────────────┐  │
              │ 아직 신선한가?     │  │
              └───┬─────────┬────┘  │
                 예        아니오    │
                  │          │      │
                  ▼          ▼      ▼
             ┌────────┐ ┌─────────────────┐ ┌──────────────────┐
             │ 바로    │ │ 묵은 값을 그대로  │ │ 지금 InfluxDB 에  │
             │ 응답    │ │ 응답하고         │ │ 물어서 응답하고    │
             │        │ │ 뒤에서 갱신      │ │ 캐시에 저장        │
             └────────┘ └─────────────────┘ └──────────────────┘
              hitFresh      hitStale             missCold
                            (사용자는 안 기다림)  (유일하게 느린 길)
```

### 3-1. "신선하다" 의 기준은 조회가 정한다

캐시 항목의 fresh window 는 그 조회의 `group_time` 입니다.

| 조회 | fresh window | 이유 |
|---|---|---|
| `range=1h, group_time=1m` | 60초 | 1분에 점이 하나 생기므로 |
| `range=7d, group_time=1h` | 3600초 | 1시간에 점이 하나 생기므로 |
| `group_time` 없음 / 못 읽음 | 60초 (하한) | 판단 근거가 없으면 짧게 |

하한·상한은 `min-bucket-seconds`(기본 60) / `max-bucket-seconds`(기본 3600) 로 조절합니다.

> **설정 이름 주의**
> 이름에 `bucket` 이 들어가지만 **시간 구간(bucket)을 뜻하지 않습니다.** fresh window 의 하한·상한입니다.
> 이름은 예전 설계의 잔재입니다 (→ [8장](#8-지금-알려진-한계)).

### 3-2. 캐시 키에 시각이 들어가지 않는다

키는 `(네임스페이스 / 인프라 / 노드 / 조회조건 서명 / fresh window)` 입니다.
`MonitoringCacheKey.java:23`

- **조회조건 서명**: measurement, range, group_time, limit, group_by, 함수·필드, 나머지 조건을
  순서에 상관없이 같은 문자열로 만듭니다. ns/infra/node 는 이미 키에 따로 들어가므로 서명에서 뺍니다.
- **시각은 키에 없습니다.** 같은 조회는 항상 같은 칸 하나를 쓰고, 그 칸의 내용이 시간이 지나며 갱신됩니다.

시각을 키에 넣으면 두 가지가 같이 망가집니다. 구간이 넘어가는 순간 **모든 조회가 한꺼번에 miss** 가
되어 InfluxDB 로 몰리고(절벽), 그 구간 안에서는 값이 갱신되지 않아 화면이 멈춥니다.
"만료 시각" 을 키가 아니라 **항목의 수명**으로 옮기면 만료 시점이 항목마다 흩어져 절벽이 없어집니다.

### 3-3. 만료돼도 기다리게 하지 않는다 (stale-while-revalidate)

fresh window 가 지난 항목을 버리지 않습니다.

```
  로드                fresh window 끝                 hard TTL(15분)
   ●───────────────────────┼──────────────────────────────┤
   │◄──── 그냥 반환 ──────►│◄─ 반환하며 뒤에서 갱신 ──────►│ 이후 폐기
        (hitFresh)              (hitStale)                  (다음 요청은 missCold)
```

만료는 "이 값이 틀렸다" 가 아니라 "슬슬 새로 받을 때가 됐다" 는 뜻입니다. 사용자를 기다리게 할
이유가 없습니다. 갱신은 전용 스레드 풀(기본 8개)에서 돌고, 같은 항목에 대해서는 동시에 하나만 돕니다.

갱신이 계속 실패하는데 무한정 옛날 값을 줄 수는 없으므로, `hard-ttl-seconds`(기본 900초)가 지나면
항목을 아예 버립니다. 다음 요청은 정상적으로 다시 읽습니다.

### 3-4. 같은 키는 동시에 한 번만 읽는다 (single-flight)

같은 조회로 요청 20개가 동시에 들어와도 InfluxDB 로는 한 번만 나가고, 나머지 19개는 그 결과를
같이 받습니다. 캐시가 비어 있는 순간(재기동 직후, 신규 노드)에 요청이 몰려도 InfluxDB 를
동시에 두들기지 않습니다.

### 3-5. 빈 결과도 캐싱한다

GPU 없는 노드에 `dcgm` 을 물어보면 **정상적으로** 빈 결과가 나옵니다.
빈 결과를 캐시 적중으로 안 치면 그 조합은 영원히 매 요청마다 InfluxDB 로 나갑니다.

지금은 빈 결과도 `empty-ttl-seconds`(기본 60초) 동안 기억합니다. 짧게 잡아서, 이제 막 데이터를
보내기 시작한 노드가 늦게 보이지 않게 했습니다.

### 3-6. 언제 지워지나

- **개수가 아니라 용량으로** 관리합니다. 전체 합이 `max-weight-mb`(기본 512MB)를 넘으면 오래 안 쓰인
  것부터 버립니다. 자주 보는 항목이 자연히 남습니다.
- 용량 계산은 데이터 점 하나를 `estimated-bytes-per-point`(기본 200바이트)로 잡은 추정값입니다.
  실측이 아니므로 실제 힙 사용량과는 차이가 납니다.

## 4. 보조 캐시 - InfluxDB 왕복 줄이기

그래프 하나를 그리는 데 데이터 조회 말고도 사전 확인이 붙습니다. 이 사전 확인은 거의 바뀌지 않으므로
따로 기억해 둡니다.

```
 요청 ──► ① 이 DB 의 기본 보관정책은?   ─┐
      ──► ② 이 노드가 InfluxDB 에 있나?  ├─ 전부 메모리에서 답 (왕복 없음)
      ──► ③ 장기 DB 에 데이터가 있나?    ─┘
      ──► ④ 진짜 데이터 조회 ───────────► InfluxDB (엔드포인트당 접속 1개 재사용)
```

| 무엇을 | 기억 시간 | 이유 |
|---|---|---|
| 보관정책 | 1시간 | 사실상 안 바뀜 |
| 자원 존재 여부 (있음) | 60초 | |
| 자원 존재 여부 (없음) | 15초 | 이제 막 올라온 노드가 빨리 보이도록 짧게 |
| 노드별 측정항목 목록 | 10분 | 예열이 매 틱마다 다시 묻지 않도록 |

`InfluxClientProvider` 는 InfluxDB 주소+계정마다 **HTTP 클라이언트 하나를 만들어 계속 재사용**합니다.
커넥션 풀·소켓·TLS 핸드셰이크를 매 조회마다 새로 하지 않습니다.
통계의 `influxSharedClients` 가 InfluxDB 인스턴스 수와 같으면 정상입니다.

## 5. 예열(warming) - 사용자보다 먼저 채워두기

세 작업이 각자의 스레드 풀에서 돕니다.

| 작업 | 주기(기본) | 데우는 조회 | 이 항목을 읽는 클라이언트 |
|---|---|---|---|
| `overview` | 매 1분 | 화면 개요가 보내는 모양 그대로 (cpu·mem·disk, 1h/1m, group_by=node_id, limit=2000) | **있음** - 화면 개요 |
| `realtime` | 매 1분 | 1h/1m, 6h/5m, 12h/5m 을 집계 없이 `SELECT *` | **없음** ([8장](#8-지금-알려진-한계)) |
| `longrange` | 매시 5분 | 1d/5m, 3d/15m, 5d/30m, 7d/1h 을 집계 없이 `SELECT *` | **없음** ([8장](#8-지금-알려진-한계)) |

예열이 지켜야 하는 것 네 가지입니다.

**① 예열은 캐시를 덮어쓴다.** 일반 조회 경로가 아니라 강제 갱신 경로(`refreshMetricsByVM`)로 갑니다.
일반 경로로 가면 캐시에 값이 있을 때 그대로 반환하고 끝나므로, **첫 틱에 한 번 채운 뒤로는 아무 일도
하지 않게 됩니다.** 다만 아직 신선한 항목은 다시 읽지 않고 건너뜁니다(로그의 `skipped`).

**② 대상은 "실제로 조회된 노드".** 최근 15분간 조회 횟수 상위 N개(기본 10)를 고릅니다.
생성 시각은 수요를 나타내지 못합니다. 운영자가 지금 열어놓고 보는 노드가 몇 달 전 생성분일 수 있습니다.
트래픽이 아직 없으면(재기동 직후) 생성 시각 순으로 채웁니다.

**③ 그 노드가 실제로 보내는 측정항목만.** 노드마다 어떤 measurement 를 보내는지 먼저 확인해서
(10분 기억) 존재하는 조합만 데웁니다. 전체 measurement × 전체 노드를 도는 방식은 대부분이 빈 결과입니다.

**④ 스케줄러를 막지 않는다.** 예열은 스케줄러 스레드와 분리해 돌리고, 45초를 넘기면 남은 작업을
포기하고, 0~10초 랜덤 지연으로 정각 몰림을 흩고, 이전 패스가 아직 돌고 있으면 이번 틱은 건너뜁니다.
스프링 스케줄러는 기본이 스레드 1개라 여러 작업이 같은 정각에 트리거되면 줄줄이 밀립니다
(`spring.task.scheduling.pool.size` 를 4로 올려 둔 이유도 같습니다).

## 6. CSP 모니터링 캐시

cb-spider 를 거쳐 클라우드 API 에서 가져오는 사용량 응답을 담습니다. 개요 화면은 탭을 열 때마다
**지표 여러 개 × 노드 여러 대** 만큼 조회를 쏟아내고 그때마다 클라우드 API 까지 다녀오므로 느립니다.

| 항목 | 값 |
|---|---|
| 키 | (VM인지 클러스터노드인지 / 대상 이름 / 지표 / 커넥션 / 몇 시간 전부터 / 몇 분 간격) |
| 축출 | **개수 기준** 최대 1만 개 |
| 유효기간 | 5분 (예열 주기 1분·5분보다 길어서 갱신 사이에도 유효) |
| 빈 응답 | **저장하지 않음** - 잠깐 비어서 온 응답이 멀쩡한 값을 덮어쓰지 않도록 |
| 예열 | 스레드 30개, 네임스페이스당 최근 노드 20개, `aws`·`azure`·`gcp` 커넥션만 |
| 예열 주기 | realtime 매 1분 (1h/6h/12h 전), longrange 매 5분 (1d/3d/5d/7d 전) |
| 토폴로지 목록 | 커넥션·클러스터 목록을 5분 기억해 cb-tumblebug 과부하를 피함 |

메트릭 캐시와 달리 **single-flight 가 없습니다.** 같은 키에 동시 miss 가 나면 그 수만큼 cb-spider 를
호출합니다 ([8장](#8-지금-알려진-한계)).

## 7. 청크 캐싱 (기본 꺼짐)

시계열의 **지나간 구간은 변하지 않습니다.** "최근 1시간" 을 조각으로 나눠 두면 1분 뒤에 새로 읽어야
할 것은 양쪽 끝뿐입니다.

```
[기본]      1분 지날 때마다 1시간을 통째로 다시 읽음
            ├──────────────── 1시간 전부 재조회 ────────────────┤

[청크 캐싱] 안 변하는 가운데는 재사용
            ├─끝─┼─ 재사용 ─┼─ 재사용 ─┼─ 재사용 ─┼─ 재사용 ─┼─끝─┤
             ↑ 이 둘만 실제로 조회
```

**기본은 꺼져 있습니다.** 사용자가 기다리는 시간은 이미 3장의 장치들로 해결돼 있고, 이건
**InfluxDB 가 훑는 데이터 양**을 줄이는 장치입니다. InfluxDB 부하가 실제로 문제일 때만 켜고,
켠 뒤에는 `chunk.sliceHits` 가 `sliceMisses` 보다 뚜렷하게 큰지 확인하세요.

집계 함수가 없거나, `limit` 이 잘라낼 수 있거나, 구간이 너무 짧으면 자르지 않고 원래대로 조회합니다.
자세한 조건과 지표는 [상세 문서 4장](../../java/mc-o11y-manager/docs/monitoring-cache.md#4-청크-캐싱-기본-off)에 있습니다.

## 8. 지금 알려진 한계

문서를 읽고 코드를 열었을 때 어긋나 보이는 지점들입니다. 고쳐진 것이 아니라 **현재 상태**입니다.

### realtime · longrange 예열이 채운 항목은 아무도 읽지 않는다

이 두 작업은 `fields` 를 비워서 요청을 만듭니다(`MonitoringCacheWarmScheduler.java:438`).
`fields` 가 비면 InfluxQL 은 집계 없는 `SELECT *` 가 되고, `GROUP BY time()` 도 `limit` 도 붙지 않습니다.

```
예열이 보내는 쿼리 : select time as timestamp, * from autogen.cpu where time > now() - 12h order by time desc
화면이 보내는 쿼리 : select time as timestamp, mean(usage_idle) as usage_idle from autogen.cpu
                     where time > now() - 1h group by time(1m), node_id order by time desc limit 2000

예열 캐시 키 서명 : m=cpu|r=12h|gt=5m|lim=
화면 캐시 키 서명 : m=cpu|r=1h|gt=1m|lim=2000|gb=node_id|f=mean:usage_idle
```

메트릭 조회 엔드포인트를 쓰는 클라이언트는 화면, insight(이상탐지·예측), GPU 조회 넷인데
**넷 다 항상 집계 함수를 붙여 보냅니다.** 따라서 두 작업이 채운 항목과 키가 겹치는 클라이언트가
없습니다. `overview` 작업이 따로 있는 이유가 이것이고, 그 작업만 실제로 화면이 읽는 항목을 채웁니다.

부수 효과가 둘 있습니다.

- 집계 없이 raw 를 읽으므로 InfluxDB 가 훑는 양이 큽니다. 에이전트 수집 주기가 30초
  (`config/.../telegraf/etc/telegraf.conf:7`) 이므로 12시간이면 계열당 1440 시점이고,
  measurement 당 계열이 여럿입니다 (계산값, 실측 아님).
- 그렇게 읽은 결과가 512MB 용량 예산을 함께 나눠 쓰므로, 화면이 실제로 읽는 항목이 밀려날 수 있습니다.

### 코드 주석·설정 주석 세 곳이 폐기된 설계를 설명한다

키에서 시각을 뺀 것이 현재 설계인데(`MonitoringCacheKey.java:12`), 아래 셋은 아직 "시간 버킷을
키에 넣는다" 고 적혀 있습니다. 읽는 사람이 반대로 이해합니다.

| 위치 | 적힌 내용 |
|---|---|
| `MonitoringCacheService.java:32` | "cache key carries a time bucket … rotates its key once a minute" |
| `MonitoringCacheProperties.java:12` | "Cache entries are keyed by a time bucket" |
| `application.yaml:160` | "rotates its cache key once a minute instead of once an hour" |

`min-bucket-seconds` / `max-bucket-seconds` 라는 이름 자체도 같은 잔재입니다.
실제로는 fresh window 의 하한·상한입니다.

`VmCreatedTimeResolver.java:19` 도 "메트릭 캐시가 항목별 TTL 을 계산하려고 쓴다" 고 적혀 있으나,
지금은 예열 대상을 생성순으로 채울 때만 쓰입니다.

### 청크 경로는 단일 쿼리와 구간이 다르다

단일 쿼리는 `time > now() - range` 이고, 청크 경로는 끝을 집계 간격 경계로 내립니다
(`alignedEnd = floor(now/step)*step`, `start = alignedEnd - range`).
`step=1m` 일 때 두 구간은 최대 1분 어긋나고, **아직 채워지는 중인 마지막 버킷이 청크 결과에서 빠집니다.**

```
단일 쿼리 : [now-3600,      now      )
청크 합계 : [alignedEnd-3600, alignedEnd)     ← now 보다 최대 step 만큼 이르다
```

부분 버킷을 빼는 것 자체는 그래프상 합리적일 수 있지만, 코드 주석의 "결과가 완전히 동일함이
증명될 때만 자른다"(`ChunkedMetricQuery.java:51`) 와는 맞지 않습니다. 기본이 꺼져 있어 지금 영향은
없습니다.

### CSP 캐시에는 single-flight 가 없다

`CspCacheService.getOrLoad` 는 miss 일 때 그냥 loader 를 호출합니다(`CspCacheService.java:60`).
개요 화면은 지표 여러 개 × 노드 여러 대를 동시에 던지므로, 캐시가 빈 상태에서 탭을 열면
그 수만큼 cb-spider 호출이 동시에 나갑니다. 메트릭 캐시에는 있는 보호가 여기에는 없습니다.

### 캐시 단위 테스트가 실행되지 않는다

`MonitoringCacheServiceTest`(7개) 와 `ChunkedMetricQueryTest`(11개) 가 있으나,
**같은 소스셋의 다른 파일 3개가 컴파일되지 않아 `./gradlew test` 가 테스트 실행 전에 멈춥니다.**
2026-06-09 의 MCI/VM → Infra/Node 리네임 이후 계속된 상태이고 캐시 작업과는 무관합니다.
그 3개를 뺀 상태에서는 18개가 전부 통과합니다.

| 깨진 파일 | 원인 |
|---|---|
| `service/VMServiceImplTest.java` | `findByNsIdAndMciIdAndVmId`, `getVmId` 가 없음 |
| `controller/OtelJavaControllerTest.java` | `ResultDTOBuilder.mciId` 가 없음 |
| `controller/BeylaControllerTest.java` | 위와 동일 |

### 슬라이스 캐시에는 용량 상한이 없다

메트릭 캐시는 바이트 추정으로 축출하지만, 청크 슬라이스 캐시는 **개수 상한(2만 개)만** 있습니다
(`ChunkedMetricQueryService.java:48`). 계열이 많은 조회를 켜 두면 개수는 여유가 있는데 힙만 커질 수 있습니다.

### 매니저를 여러 대로 늘리면 공유되지 않는다

캐시는 전부 프로세스 메모리 안입니다.

- 매니저 두 대는 캐시를 공유하지 않습니다. 각자 데우고 각자 답합니다.
- "캐시 비우기" 를 호출해도 **그 요청을 받은 한 대만** 비워집니다.
- 적중률 통계도 매니저마다 따로입니다.

매니저 한 대로 쓰는 기본 구성에서는 문제가 없습니다. 여러 대로 늘릴 때에만 외부 공유 캐시가 필요합니다.

## 9. 잘 돌고 있는지 보는 법

```bash
curl -s http://<매니저>:18080/api/o11y/monitoring/influxdb/cache/stats | jq
```

| 필드 | 뭘 보나 |
|---|---|
| `hitRate` | 적중률. 낮으면 예열 대상이나 fresh window 를 의심 |
| `hitFreshCount` / `hitStaleCount` | stale 이 많으면 예열이 못 따라가는 것 |
| `servedAgeAvgMillis` / `servedAgeMaxMillis` | **실제로 내보낸 데이터가 얼마나 묵었는지.** 화면이 안 갱신되는 문제는 여기서 잡힙니다 |
| `emptyCachedCount` | 빈 결과 기억 횟수. 과도하면 예열 대상 점검 |
| `refreshFailedCount` | 뒤에서 갱신하다 실패한 횟수. 0이 아니면 InfluxDB 상태 확인 |
| `evictionCount` | 용량 부족 축출. 계속 늘면 `max-weight-mb` 상향 검토 |
| `influxSharedClients` | 공유 접속 수. InfluxDB 인스턴스 수와 같아야 정상 |
| `influxMeta.*` | 보조 캐시 적중. hits 가 misses 보다 훨씬 커야 정상 |
| `warm.passesSkippedOverlap` / `warm.passesTimedOut` | 예열이 주기 안에 못 끝나고 있다는 신호 |
| `trackedVmCount` | 조회 이력이 잡힌 노드 수. 0이면 예열이 생성순 폴백으로 도는 중 |
| `chunk.*` | 청크 캐싱을 켠 경우에만 의미 있음 |

관리 API 입니다.

| 방법 | 경로 | 하는 일 |
|---|---|---|
| `GET` | `/api/o11y/monitoring/influxdb/cache/stats` | 위 통계 |
| `DELETE` | `/api/o11y/monitoring/influxdb/cache` | 메트릭 캐시 + 슬라이스 캐시 비우기 |
| `POST` | `/api/o11y/monitoring/influxdb/cache/warm` | 지금 즉시 예열 (완료까지 대기) |

CSP 캐시는 `CspMonitoringController` 아래에 `GET …/cache/stats` 와 `DELETE …/cache` 만 있습니다.
즉시 예열 버튼은 없고 정해진 주기로만 돕니다.

설정값 전체와 상황별 조절 가이드는
[`java/mc-o11y-manager/docs/monitoring-cache.md`](../../java/mc-o11y-manager/docs/monitoring-cache.md) 를 보세요.
