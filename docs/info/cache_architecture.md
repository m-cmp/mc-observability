# 캐시 구조 이해하기 (mc-o11y-manager)

이 문서는 매니저(`java/mc-o11y-manager`)가 화면을 빠르게 보여주려고 어떻게 **캐시(미리 저장해 둔
임시 결과)** 를 쓰는지 설명합니다.

> 모니터링 메트릭 캐시의 더 자세한 내용(설계 근거, 지표 해석, 튜닝)은
> [`java/mc-o11y-manager/docs/monitoring-cache.md`](../../java/mc-o11y-manager/docs/monitoring-cache.md)를 보세요.

## 캐시가 뭐고 왜 쓰나요?

대시보드를 열면 매니저는 매번 **InfluxDB(메트릭 저장소)** 나 **cb-spider(클라우드에서 사용량을
가져오는 도구)** 에 물어봐서 그래프를 그립니다. 그런데 여러 사람이 같은 화면을 자주 열면, 똑같은
질문을 계속 던지게 되고 그때마다 느려집니다.

그래서 한 번 가져온 답을 잠깐 메모리에 적어두고, 같은 질문이 또 오면 **저장소에 다시 묻지 않고
적어둔 답을 바로 돌려줍니다.** 이게 캐시입니다. 카페에서 자주 나가는 메뉴를 미리 만들어 두는 것과
비슷합니다.

이 프로젝트에서 알아둘 점 세 가지:

- 캐시는 [Caffeine](https://github.com/ben-manes/caffeine)이라는 자바 라이브러리로 **직접** 만들었습니다.
  (스프링의 자동 캐시 기능 `@Cacheable`은 쓰지 않습니다.)
- 캐시는 전부 **매니저 프로그램 한 개의 메모리 안**에만 있습니다. 매니저가 꺼지면 사라집니다.
- 주로 쓰는 캐시는 **두 개**입니다.
  1. **모니터링 메트릭 캐시** — InfluxDB에서 가져온 그래프 데이터를 저장
  2. **CSP 모니터링 캐시** — cb-spider에서 가져온 클라우드 사용량을 저장

그리고 각 캐시에는 **워머(warmer, 미리 데워두는 일꾼)** 가 붙어 있습니다. 사용자가 화면을 열기
전에 미리 자주 보는 VM의 데이터를 가져다 채워 둬서, 처음 열 때부터 빠르게 보이도록 합니다.

```
                    ┌──────────────── 매니저 프로그램 (메모리 안) ────────────────┐
                    │                                                            │
  사용자 / 화면      │   InfluxDBController                                       │
  ─────────────────►│        │                                                   │
  (VM 대시보드)      │        ▼                                                   │
                    │   [모니터링 메트릭 캐시] ──── 없거나 오래됐으면 ────► InfluxDB
                    │        ▲     있으면 바로 응답                               │
                    │        │                                                   │
                    │   [워머] 사용자가 열기 전에 미리 채워 둠                      │
                    │                                                            │
                    │   CspMonitoringController                                  │
  ─────────────────►│        │                                                   │
  (클라우드 사용량)  │        ▼                                                   │
                    │   [CSP 모니터링 캐시] ─── 없으면 ───► cb-spider ─► 클라우드 API
                    │        ▲     있으면 바로 응답                               │
                    │        │                                                   │
                    │   [워머]                                                   │
                    └────────────────────────────────────────────────────────────┘
```

> **용어 한 줄 정리**
> - **TTL(유효기간)**: 저장한 값이 살아있는 시간. 지나면 버려집니다.
> - **워밍(warming)**: 사용자가 보기 전에 미리 캐시를 채워 두는 것.
> - **히트(hit) / 미스(miss)**: 물어봤을 때 캐시에 있으면 히트, 없어서 저장소까지 가야 하면 미스.
> - **무효화(invalidate)**: 저장해 둔 값을 전부 지우는 것.

## 1. 모니터링 메트릭 캐시 (InfluxDB 그래프 데이터)

InfluxDB에서 가져온 그래프 데이터를 저장해서, **같은 조회가 또 오면 InfluxDB에 다시 묻지 않고**
바로 돌려줍니다.

| 항목 | 위치 |
|---|---|
| 캐시 본체 | `service/cache/MonitoringCacheService.java` |
| 저장 이름표(키) | `service/cache/MonitoringCacheKey.java` |
| 설정 | `config/MonitoringCacheProperties.java` (`monitoring.cache.*`) |
| 미리 데우는 일꾼 | `service/cache/MonitoringCacheWarmScheduler.java` |
| 조회 이력 추적 | `service/cache/QueryAccessTracker.java` |
| InfluxDB 접속 공유 | `service/influx/InfluxClientProvider.java` |
| 보조 조회 기억 | `service/influx/InfluxMetaCache.java` |
| 사용하는 곳 | `service/InfluxDbServiceImpl.java`의 메트릭 조회 |
| 관리 API | `controller/InfluxDBController.java` |

### 1-1. 요청 하나가 지나가는 길

가장 중요한 그림입니다. 요청이 오면 **세 갈래** 중 하나로 갑니다.

```
                          요청 도착
                             │
                             ▼
                   ┌──────────────────┐
                   │ 캐시에 있나?      │
                   └────┬────────┬────┘
                     있음         없음
                        │           │
                        ▼           │
              ┌──────────────────┐  │
              │ 아직 신선한가?     │  │
              └───┬─────────┬────┘  │
                 예        아니오    │
                  │          │      │
                  ▼          ▼      ▼
             ┌────────┐ ┌─────────────────┐ ┌──────────────────┐
             │ 바로    │ │ 일단 옛날 값을    │ │ 지금 InfluxDB에   │
             │ 응답    │ │ 그대로 응답하고   │ │ 물어서 응답하고    │
             │        │ │ 뒤에서 몰래 갱신  │ │ 캐시에 저장        │
             └────────┘ └─────────────────┘ └──────────────────┘
              hitFresh      hitStale             missCold
              (가장 빠름)   (사용자는 안 기다림)   (유일하게 느린 길)
```

핵심은 가운데 갈래입니다. **유효기간이 지났다는 이유만으로 사용자를 기다리게 하지 않습니다.**
이걸 stale-while-revalidate(오래된 걸 주면서 뒤에서 새로 받기)라고 부릅니다.

### 1-2. "신선하다"는 기준은 조회가 스스로 정합니다

그래프를 요청할 때는 **몇 분 간격으로 묶어서 볼지**(`group_time`)를 같이 보냅니다.
1분 간격으로 요청했다면, **새 데이터 점은 1분에 한 번만 생깁니다.** 그러니 1분 안에는 몇 번을
물어도 사실상 같은 답입니다. 이 성질을 그대로 유효기간으로 씁니다.

| 조회 | 유효기간 | 이유 |
|---|---|---|
| 1시간 그래프, 1분 간격 | **60초** | 1분마다 점이 하나 생기니까 |
| 7일 그래프, 1시간 간격 | **3600초** | 1시간마다 점이 하나 생기니까 |
| 간격을 안 보냈을 때 | 60초 (하한) | 판단 근거가 없으니 짧게 |

```
[예전 방식] — 시간을 1시간 칸으로 잘라서 저장

  0분        10분       20분       30분       40분       50분    59분
  ●───────────────────────────────────────────────────────────────►
  캐시 채움    화면에 계속 이 시점 데이터가 나옴 (그동안 새 데이터는 계속 쌓이는데)
                                                        └─ 최대 59분 묵은 값


[지금 방식] — 조회가 정한 만큼만 신선

  0분   1분   2분   3분   4분   5분  ...
  ●──┐  ●──┐  ●──┐  ●──┐  ●──┐  ●
     갱신   갱신   갱신   갱신   갱신
  └─ 항상 1분 이내
```

### 1-3. 같은 조회인지 어떻게 구분하나요 (저장 이름표)

이름표는 `(어느 네임스페이스 / 어느 인프라 / 어느 노드 / 어떤 조회조건 / 유효기간)` 으로 만듭니다.

- **"어떤 조회조건"** : measurement, range, group_time, limit, group_by, 함수/필드 같은 조건을
  순서에 상관없이 똑같은 문자열로 만듭니다. (ns/infra/node는 이미 이름표에 따로 들어가므로 여기선 뺍니다.)
- **이름표에 시각은 들어가지 않습니다.** 같은 조회는 **항상 같은 칸 하나**를 쓰고, 그 칸의 내용이
  시간이 지나며 갱신됩니다.

> **왜 시각을 뺐나요?**
> 예전에는 이름표에 "몇 시 구간"이 들어 있었습니다. 그러면 시간이 넘어가는 순간 **모든 조회가
> 한꺼번에 미스**가 되어 InfluxDB로 몰립니다. 그리고 그 칸 안에서는 데이터가 갱신되지 않아
> 위 그림처럼 오래된 값이 계속 나옵니다. 이름표에서 시각을 빼고 "유효기간"으로 바꾸니
> 두 문제가 같이 없어졌습니다.

### 1-4. 여러 명이 동시에 물어봐도 InfluxDB엔 한 번만

```
[예전]                              [지금]

요청 1 ──────► InfluxDB             요청 1 ──┐
요청 2 ──────► InfluxDB             요청 2 ──┤
요청 3 ──────► InfluxDB             요청 3 ──┼──► InfluxDB (한 번만)
   ⋮                                   ⋮     │
요청 20 ─────► InfluxDB             요청 20 ─┘
                                             └─ 나머지는 그 결과를 같이 받음
   20번 조회                           1번 조회
```

캐시가 비어 있는 순간(매니저 재시작 직후, 새 VM 등)에 요청이 몰리면 예전에는 그 수만큼
InfluxDB를 두들겼습니다. 지금은 같은 이름표에 대해 **한 번만** 읽고 나머지는 그 결과를 공유합니다.

### 1-5. 한 번 물어볼 때 InfluxDB에 몇 번 다녀오나

그래프 하나를 그리려면 예전에는 InfluxDB를 **3~4번** 다녀와야 했습니다.

```
[예전] — 캐시에 없을 때마다 매번

  요청 ──► ① "이 DB의 기본 보관정책이 뭐지?"  ──► InfluxDB   (새 접속 만들고 버림)
       ──► ② "이 VM이 있긴 한가?"             ──► InfluxDB   (새 접속 만들고 버림)
       ──► ③ "장기 DB에 데이터 있나?"          ──► InfluxDB   (새 접속 만들고 버림)
       ──► ④ 진짜 데이터 조회                  ──► InfluxDB   (새 접속 만들고 버림)

  ①②③은 거의 바뀌지 않는 정보인데도 매번 물어봤습니다.
  게다가 매번 접속을 새로 만들었다가 버렸습니다(연결 재사용 0).


[지금]

  요청 ──► ①②③ 기억해 둔 값 사용 (InfluxDB에 안 감)
       ──► ④ 진짜 데이터 조회 ──► InfluxDB   (엔드포인트당 접속 1개를 계속 재사용)

  왕복 3~4번 → 1번
```

기억해 두는 시간은 성격에 맞춰 다르게 잡았습니다.

| 무엇을 | 얼마나 기억 | 이유 |
|---|---|---|
| 보관정책 | 1시간 | 사실상 안 바뀜 |
| VM/인프라 존재 여부 (있음) | 60초 | |
| VM/인프라 존재 여부 (없음) | 15초 | 이제 막 올라온 VM이 빨리 보이도록 짧게 |
| VM별 측정항목 목록 | 10분 | |

### 1-6. 데이터가 없는 조합도 기억합니다

GPU가 없는 VM에 GPU 지표를 물어보면 **정상적으로 빈 결과**가 나옵니다.
예전에는 이런 빈 결과를 캐시 적중으로 안 쳐서, **요청이 올 때마다 매번 InfluxDB로 나갔습니다.**

지금은 빈 결과도 **60초 동안 기억**합니다. 없는 걸 반복해서 묻지 않으면서도, 짧은 시간이라
이제 막 데이터를 보내기 시작한 VM은 금방 화면에 나타납니다.

### 1-7. 미리 데워두기 (워머)

사용자가 화면을 열기 전에 미리 캐시를 채워 두는 백그라운드 일꾼입니다.

| 작업 | 주기(기본) | 무엇을 데우나 |
|---|---|---|
| `realtime` | 매 1분 | 최근 1시간 / 6시간 / 12시간 그래프 |
| `longrange` | 매시 5분 | 1일 / 3일 / 5일 / 7일 그래프 (장기 데이터는 다운샘플링 DB에서) |
| `overview` | 매 1분 | NS/MCI 개요 화면이 쓰는 cpu·mem·disk 그래프 |

> 왜 `overview`가 따로 있나요? `realtime`이 데워 두는 형태와 개요 화면이 실제로 보내는 조회 형태가
> 조금 달라서, 그대로 두면 매번 미스가 납니다. 그래서 화면이 쓰는 형태 그대로 미리 데워 둡니다.

**① 워머는 캐시를 덮어씁니다**

```
[예전]

  1분: 워머 ─► "캐시에 있어?" ─► 있네 ─► 그대로 반환하고 끝    ← 아무 일도 안 함
  2분: 워머 ─► "캐시에 있어?" ─► 있네 ─► 그대로 반환하고 끝    ← 아무 일도 안 함
   ⋮                                                        ⋮
 59분:                                        데이터는 여전히 0분 시점 것

  → 매분 도는 일꾼이 사실상 놀고 있었습니다.


[지금]

  1분: 워머 ─► InfluxDB에서 새로 읽어 덮어씀  ●
  2분: 워머 ─► InfluxDB에서 새로 읽어 덮어씀  ●
   ⋮
  (단, 아직 신선한 항목은 건너뜁니다 → 로그의 skipped)
```

**② 데울 대상은 "실제로 보고 있는 VM"**

```
[예전] 최근에 만들어진 VM 순서로 10개
        └─ 그런데 사람들이 보는 VM은 몇 달 전에 만든 것일 수도 있습니다.

[지금] 최근 15분간 실제로 조회된 VM을 조회 횟수 순으로 10개
        └─ 트래픽이 아직 없으면(재시작 직후) 최근 생성순으로 채웁니다.
```

**③ 그 VM이 실제로 보내는 항목만 데웁니다**

```
[예전]  대상 VM 10개  ×  전체 측정항목 12개  ×  구간 3개  =  360번 조회
        (GPU 없는 VM에 GPU 지표를, 윈도우 VM에 리눅스 지표를 물어봄 → 대부분 빈 결과)

[지금]  VM마다 "너는 어떤 항목을 보내니?"를 먼저 확인(10분 기억)하고
        실제 있는 조합만 데웁니다.
```

**④ 스케줄러를 막지 않습니다**

- 데우는 작업은 스케줄러 스레드와 **분리**되어 돕니다.
- 45초를 넘기면 남은 작업을 포기합니다.
- 0~10초 랜덤 지연을 줘서 여러 작업이 정각에 한꺼번에 몰리지 않게 합니다.
- 이전 작업이 아직 돌고 있으면 이번 차례는 건너뜁니다.

> 예전에는 스케줄러 스레드가 **1개**뿐인데 매분 0초에 여러 작업이 동시에 시작되고 각자 끝날 때까지
> 기다렸습니다. 하나가 밀리면 나머지가 줄줄이 밀렸습니다. 지금은 스레드를 4개로 늘리고, 기다리지도
> 않습니다.

### 1-8. 언제 지워지나요

- **개수가 아니라 용량(메모리 크기)으로 관리**합니다. 전체 합이 기본 **512MB**를 넘으면, 오래 안
  쓰인 것부터 자동으로 버립니다. 즉 자주 보는 VM 데이터가 자연스럽게 남습니다.
- 갱신이 계속 실패해서 옛날 값만 계속 내보내는 상황을 막으려고, **15분**이 지나면 항목을 아예
  버립니다. 다음 요청은 정상적으로 새로 읽습니다.

> **예전에 있던 함정**
> 예전에는 유효기간을 "VM 생성시각 + 7일"로 계산해서, **만들어진 지 7일이 넘은 VM은 아예 캐시에
> 넣지 않았습니다.** 실제 운영 환경의 VM은 대부분 7일보다 오래됐으므로, 결과적으로 **캐시가 거의
> 동작하지 않았습니다.** 지금은 생성시각으로 저장 여부를 가르지 않습니다.

### 1-9. 조각내서 재사용하기 (청크 캐싱, 기본 꺼짐)

시계열의 **지나간 구간은 변하지 않습니다.** 그래서 "최근 1시간"을 조각으로 나눠 두면, 1분이
지났을 때 새로 읽어야 할 건 양쪽 끝뿐입니다.

```
[기본]      1분 지날 때마다 1시간을 통째로 다시 읽음
            ├──────────────── 1시간 전부 재조회 ────────────────┤

[청크 캐싱] 안 변하는 가운데는 재사용
            ├─끝─┼─ 재사용 ─┼─ 재사용 ─┼─ 재사용 ─┼─ 재사용 ─┼─끝─┤
             ↑ 이 둘만 실제로 조회
```

기본은 **꺼져 있습니다.** 사용자가 기다리는 시간은 이미 앞의 장치들(즉시 응답 + 뒤에서 갱신)로
해결돼 있고, 이건 **InfluxDB가 훑는 데이터 양**을 줄이는 장치라서 InfluxDB 부하가 실제로 문제일
때만 켜면 됩니다. 켜는 법과 지표 보는 법은
[상세 문서 10장](../../java/mc-o11y-manager/docs/monitoring-cache.md)에 있습니다.

> 결과가 완전히 같다고 보장되지 않는 조회(집계 함수가 없거나, `limit`이 잘라낼 수 있거나, 구간이
> 너무 짧은 경우)는 **자르지 않고 원래대로** 조회합니다.

### 1-10. 관리 API (`InfluxDBController`)

| 방법 | 경로 | 하는 일 |
|---|---|---|
| `GET` | `/api/o11y/monitoring/influxdb/cache/stats` | 적중률, 저장 개수, 내보낸 데이터가 얼마나 묵었는지 등 |
| `DELETE` | `/api/o11y/monitoring/influxdb/cache` | 캐시 전부 비우기 |
| `POST` | `/api/o11y/monitoring/influxdb/cache/warm` | 지금 당장 미리 데우기 실행 |

## 2. CSP 모니터링 캐시 (cb-spider 클라우드 사용량)

cb-spider에서 가져온 클라우드 사용량 응답을 저장합니다. NS/MCI 개요 화면은 탭을 한 번 열 때마다
**약 8개 지표 × VM 여러 대** 만큼 조회를 쏟아내고, 그때마다 cb-spider가 클라우드 API까지 다녀오기
때문에 느립니다. 이 반복 조회를 짧은 시간 동안 캐시가 대신 받아 줍니다.

| 항목 | 위치 |
|---|---|
| 캐시 본체 | `service/cache/CspCacheService.java` |
| 저장 이름표(키) | `service/cache/CspCacheKey.java` |
| 설정 | `config/CspCacheProperties.java` (`csp.cache.*`) |
| 미리 데우는 일꾼 | `service/cache/CspCacheWarmScheduler.java` |
| 사용하는 곳 | `controller/CspMonitoringController.java` |

### 같은 조회인지 어떻게 구분하나요

이름표는 `(VM인지 클러스터노드인지 / 대상 이름 / 지표 / 커넥션 / 몇 시간 전부터 / 몇 분 간격)`
으로 만듭니다.

### 언제 지워지나요

- **개수로 관리**합니다. 최대 **1만 개**까지 저장하고, 넘으면 오래된 것부터 버립니다.
- **유효기간은 5분**입니다. 워밍 주기(1분/5분)보다 길어서 갱신 사이에도 값이 유효합니다.
- **빈 응답은 저장하지 않습니다.** 잠깐 비어서 온 응답이 멀쩡히 들어있던 값을 덮어쓰지 않게 합니다.

### 미리 데워두기 (워머)

일꾼 스레드 기본 **30개**, 네임스페이스마다 최근 VM **20개**까지 데웁니다. `aws`, `azure`, `gcp`
커넥션만 대상입니다. 그리고 "어떤 커넥션·클러스터가 있는지" 목록 조회는 Tumblebug가 과부하로
막히지 않도록 **5분 동안 기억해 두고 재사용**합니다.

| 작업 | 주기(기본) | 무엇을 데우나 (몇 시간 전 / 몇 분 간격) |
|---|---|---|
| `realtime` | 매 1분 | 1시간 / 6시간 / 12시간 전 (5분 간격) |
| `longrange` | 매 5분 | 1일 / 3일 / 5일 / 7일 전 (5분 간격) |

### 관리 API (`CspMonitoringController`)

| 방법 | 경로 | 하는 일 |
|---|---|---|
| `GET` | `…/cache/stats` | 통계 보기 |
| `DELETE` | `…/cache` | 캐시 전부 비우기 |

(이 캐시에는 "지금 데우기" HTTP 버튼은 없고, 정해진 주기로만 데웁니다.)

## 3. 뒤에서 돕는 작은 캐시들

### InfluxDB 접속 공유 (InfluxClientProvider)
`service/influx/InfluxClientProvider.java` — InfluxDB 주소+계정마다 **접속 객체 하나를 만들어
계속 재사용**합니다. 예전에는 쿼리 한 번마다 새로 만들고 버려서, 연결·소켓·암호화 협상을 매번
새로 했습니다. 통계의 `influxSharedClients`가 InfluxDB 인스턴스 수와 같으면 정상입니다.

### 보조 조회 기억 (InfluxMetaCache)
`service/influx/InfluxMetaCache.java` — 보관정책, "이 VM 있나?" 확인, VM별 측정항목 목록을
기억합니다. 1-5의 ①②③이 여기에 해당합니다.

### 조회 이력 추적 (QueryAccessTracker)
`service/cache/QueryAccessTracker.java` — 최근 15분간 어떤 VM이 실제로 조회됐는지를 세어 둡니다.
워머가 "무엇을 데울지" 고를 때 씁니다.

### VM 생성시각 기억 (VmCreatedTimeResolver)
`service/cache/VmCreatedTimeResolver.java` — VM이 언제 만들어졌는지를 CB-Tumblebug에서 한 번
물어보고 **1시간 동안 기억**합니다(최대 1만 개). 지금은 **워머가 조회 이력만으로 대상을 못 채웠을 때
보조로만** 씁니다. (예전에는 캐시 유효기간 계산에도 썼지만 그 방식은 폐기했습니다 — 1-8 참고.)

### 토폴로지 목록 기억 (CSP 워머 내부)
커넥션 목록과 클러스터 목록을 **5분간 기억**해서, 워밍이 돌 때마다 매번 다시 조회하지 않습니다.

### SSH 연결 재사용 (SshServiceImpl)
대상 서버로 맺은 SSH 연결을 잠깐 보관해 두고 재사용합니다. **120초** 동안 안 쓰이면 끊습니다.
메트릭 캐시는 아니지만, 같은 "재사용으로 빨라지게 하는" 장치라 함께 적어 둡니다.

## 5. 잘 돌고 있는지 보는 법

```bash
curl -s http://<매니저>:18080/api/o11y/monitoring/influxdb/cache/stats | jq
```

| 필드 | 뭘 보나 |
|---|---|
| `hitRate` | 적중률. 낮으면 데우는 대상이나 유효기간을 의심 |
| `hitFreshCount` / `hitStaleCount` | 신선한 응답 / 묵은 응답 비율. stale이 많으면 워머가 못 따라가는 것 |
| `servedAgeAvgMillis` / `servedAgeMaxMillis` | **실제로 내보낸 데이터가 얼마나 묵었는지.** 화면이 안 갱신되는 문제는 여기서 잡힙니다 |
| `emptyCachedCount` | 빈 결과 기억 횟수. 너무 많으면 데우는 대상 점검 |
| `refreshFailedCount` | 뒤에서 갱신하다 실패한 횟수. 0이 아니면 InfluxDB 상태 확인 |
| `influxSharedClients` | 공유 접속 수. InfluxDB 인스턴스 수와 같아야 정상 |
| `influxMeta.*` | 보조 조회 기억 적중. hits가 misses보다 훨씬 커야 정상 |
| `warm.passesSkippedOverlap` / `passesTimedOut` | 데우기가 주기 안에 못 끝나고 있다는 신호 |
| `trackedVmCount` | 조회 이력이 잡힌 VM 수. 0이면 워머가 생성순 폴백으로 도는 중 |

## 6. 매니저를 여러 대로 늘리면?

캐시는 전부 매니저 **한 대의 메모리 안에만** 있습니다. 매니저를 두 대 이상으로 늘리면:

- 캐시가 **서로 공유되지 않습니다.** 각 매니저가 따로 데우고 따로 답합니다.
- "캐시 비우기"를 호출해도 **그 요청을 받은 매니저만** 비워집니다.
- 적중률 통계도 매니저마다 따로입니다.

지금처럼 매니저 한 대로 쓰는 기본 구성에서는 문제가 없습니다. 매니저를 여러 대로 늘릴 때에만
공유 캐시(예: Redis 같은 외부 캐시)가 필요해집니다.

## 7. 왜 이렇게 만들었나 (설계 의도)

- **왜 스프링 자동 캐시(`@Cacheable`)를 안 썼나?** 자동 기능으로는 표현하기 어려운 동작이 필요해서
  직접 만들었습니다: 용량 기준으로 버리기, 조회가 정하는 유효기간, 만료돼도 일단 주고 뒤에서 갱신,
  같은 조회를 한 번만 읽기, 미리 데워 두기 같은 것들입니다.
- **왜 유효기간을 조회의 집계 간격에 맞추나?** 그보다 짧게 잡으면 같은 답을 얻으려고 InfluxDB를
  더 자주 두들기게 되고, 길게 잡으면 화면에 오래된 값이 나옵니다. 집계 간격이 그 경계입니다.
- **왜 만료된 값을 그냥 버리지 않고 일단 주나?** 만료는 "이 값이 틀렸다"가 아니라 "슬슬 새로
  받을 때가 됐다"는 뜻입니다. 사용자를 기다리게 할 이유가 없습니다.
- **왜 빈 결과도 기억하나?** GPU 없는 VM에 GPU 지표를 묻는 것처럼, 없는 게 정상인 조합이 많습니다.
  기억하지 않으면 그 조합이 영원히 매번 InfluxDB로 나갑니다. 대신 짧게(60초) 잡아서 새로 들어온
  데이터가 늦게 보이지 않게 합니다.
- **왜 "실제로 조회된 VM"을 데우나?** 사람들이 보는 VM이 최근에 만든 VM이라는 보장이 없기
  때문입니다. 실제 조회 이력이 수요를 가장 잘 나타냅니다.
